# 주인공 장비 외형 시스템 — 1단계 분석과 설계안

상태: **1단계(분석·설계) 검토 대기.** 이 문서는 설계 제안이며 코드·실행 에셋은 바꾸지 않았다. 2단계(에셋 규격·예시 에셋), 3단계(코드 연동), 4단계(검증)는 사용자 승인 후 하나씩 진행한다. 기준 main `04cb6c5` (PR #37 병합 후).

## 2. 현재 모션 프레임 체계 (코드와 PNG에서 확인)

모든 주인공 실행 아틀라스는 **192px 정사각 셀**이다. 총 **14장, 102셀**.

| 모션 | 파일 | 격자 | 셀 수 | 프레임 선택 | 발 기준점(셀 px) | 그림 상자(월드 단위, ×`ACTOR_SCALE` 1.4) | 좌우 반전 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 정지 | `warrior-idle-8dir-v1.png` 768×384 | 4×2 | 8 (방향당 1) | `Hero.dir` 8구간 | (96,176) | 56 | 없음 |
| 걷기 | `warrior-walk-{n,ne,e,se,s,sw,w,nw}-v1.png` 768×384 ×8장 | 4×2 | 64 (방향당 8) | 이동 112 단위당 1주기 | (96,176) | 56 | 없음 |
| 기본 공격 | `warrior-attack-v1.png` 576×384 | 3×2 | 6 | 0.42초를 6등분 | 프레임별: 원본 512 기준 (290,470)(264,470)(310,470)(340,455)(280,464)(300,465) → 셀 px ≈ ×0.375 | 64 × 프레임별 배율 {1,1,1,1,.95,.88} | `attack_face > 0`이면 반전 (원본은 왼쪽을 봄) |
| 기술 4종 | `warrior-{cleave,sweep,thrust,retreat}-v1.png` 576×384 ×4장 | 3×2 | 24 | 0.64초를 8틱으로 나눠 표로 6프레임에 매핑(갈라베기·후퇴 `{0,1,1,2,3,4,5,5}`, 휩쓸기 `{0,0,1,2,3,3,4,5}`, 찌르기 `{0,0,1,2,3,4,5,5}`) | (116,176) | 80 | 기본 공격과 같음 |

설계에 직접 영향을 주는 사실:

- **모션마다 셀 1px이 나타내는 월드 크기가 다르다.** 정지·걷기 56/192, 공격 64×배율/192, 기술 80/192. 그래서 장비 레이어는 하나의 공통 픽셀 크기로 만들 수 없고, **각 베이스 아틀라스의 셀 공간 그대로** 만들어야 한다.
- 정지·걷기는 8방향을 따로 그린 그림이고 반전하지 않는다(오른손 칼 유지). 공격·기술은 왼쪽을 보는 한 벌을 반전해 오른쪽에 쓴다.
- 현재 그림은 두 계열이다. 정지·걷기는 청록 미늘 갑옷 + 상투, 공격·기술은 남색 긴 전포(금 용 무늬) + 파란 머리끈. 장비 레이어도 두 계열을 각각 맞춰야 한다. 두 계열을 통일하는 일은 이번 범위 밖이다.
- **환도가 모든 프레임에 그려져 있고**, 공격 #2·#3과 일부 기술 프레임에는 파란 베기 궤적이 함께 그려져 있다.
- 렌더링은 `SDL_RenderCopyExF` 한 번으로 그린다. 그 위에 무적 깜빡임(알파 110/255), 피격 번쩍임(같은 텍스처를 가산 혼합으로 한 번 더), `gfx_attack_trace` 잔상, 지붕 가림(`cover_actor` 상자 56/96/180 × 48/64/110)이 붙는다. 서장·제목 화면도 같은 `gfx_hero`를 쓴다.
- 장비 상태는 `Game.sword`, `Game.armor` 두 bool이다. 투구 아이템은 **게임에 없다**. 지금은 장착해도 외형이 바뀌지 않는다. 별도 저장 기능은 없고 수련장 진입·복귀만 두 값을 복사한다.

### 색 분리 시험 결과

자동으로 레이어를 떼어 낼 수 있는지 색으로 시험했다([개념 시트](hero-gear-anchor-concept.png)).

- 칼날(밝고 채도 낮은 은색)은 대체로 분리되지만 흰 깃·흰 테두리와 섞이고, 공격 프레임에서는 베기 궤적과 붙어 버린다.
- 갑옷의 청록·남색은 전포·바지·머리끈과 같은 색이라 색만으로는 갑옷 영역을 떼어 낼 수 없다.
- 발 기준점(초록)과 머리 위치(자홍)는 자동 추정이 맞았지만, 손잡이 위치(주황)는 여러 프레임에서 칼끝 쪽으로 잘못 잡혔다.

결론: **기준점과 마스크는 자동 추정 + 사람이 프레임별로 확인·수정**해야 한다. 2단계 작업량은 이 확인 작업이 대부분이다.

## 3. 설계안

### 3.1 무엇을 "몸체(base)"로 둘 것인가

| 방안 | 내용 | 판단 |
| --- | --- | --- |
| A. 맨몸 베이스를 새로 그림 | 갑옷·칼 없는 몸 102셀을 새로 그리고 모든 장비를 위에 얹음 | 가장 깔끔하지만 102셀 재제작은 대규모 에셋 생산이고, 승인된 주인공 그림이 바뀐다. 1차에서 제외 |
| **B. 현재 그림에서 칼만 뺀 것을 베이스로 (추천)** | 현재 프레임에서 칼날 픽셀만 지운 것이 베이스. 기본 갑옷(군영 갑주)·상투는 베이스에 남김. 기본 환도는 지운 칼날 픽셀 그대로 "기본 무기 레이어"가 됨 | 기본 외형이 **픽셀 단위로 지금과 같다**(검사로 보장 가능). 무기는 진짜로 교체되고, 갑옷·투구는 위에 덮는다 |
| C. 현재 그림 위에 덧그리기만 | 베이스 무변경, 장비를 위에 그림 | 새 칼이 기존 칼을 다 덮지 못하면 칼이 두 자루로 보인다. 제외 |

B의 한계: 갑옷은 기본 갑옷 위에 덮는 방식이라 기본보다 **작거나 얇은 갑옷은 표현할 수 없다**. 그런 장비가 필요해지면 그때 A로 넘어간다.

### 3.2 슬롯과 그리기 순서

```
[무기-뒤] → 베이스(몸·기본 갑옷) → 갑옷 → 투구 → [장신구] → 무기
```

- 1차 슬롯: **무기, 갑옷, 투구.** 망토·장신구는 슬롯 번호만 예약한다(망토는 몸 뒤에 그려야 해서 `무기-뒤`와 같은 "뒤" 단계가 필요하다).
- 가림(칼이 몸 뒤로 가는 방향, 손가락이 손잡이를 감싸는 부분, 머리끈이 투구 위로 나오는 부분)은 **에셋 준비 단계에서 미리 잘라** 둔다. 실행 중에는 위 순서대로 그리기만 하므로 깊이 정렬 계산이 없다. 1차에서 `무기-뒤`는 비워 둘 수 있다.

### 3.3 외형과 능력치 분리

새 헤더 `src/gear.h`(SDL 없음, 데이터만)를 둔다.

```c
typedef enum { GEAR_WEAPON, GEAR_ARMOR, GEAR_HELMET, GEAR_SLOT_COUNT } GearSlot;
typedef enum { LOOK_NONE, LOOK_HWANDO, LOOK_HWANDO_TEMPERED,
               LOOK_ARMOR_NUBI, LOOK_HELMET_JEONRIP, LOOK_COUNT } GearLook;
/* 아이템 → (슬롯, 외형). 스탯은 기존 ITEMS/game.c 그대로. */
typedef struct { GearSlot slot; GearLook look; } ItemLook;
void game_hero_looks(const Game *g, GearLook out[GEAR_SLOT_COUNT]);
```

- 외형은 아이템 표 `ITEMS`와 **별도 표**에서 아이템을 외형 ID로 연결한다. 같은 스탯의 두 아이템이 다른 외형을, 다른 스탯의 두 아이템이 같은 외형을 가리킬 수 있다.
- `game_hero_looks`는 기존 `Game.sword/armor`를 읽어 슬롯별 외형을 돌려준다. 해제 시 기본값(무기 `LOOK_HWANDO`, 갑옷·투구 `LOOK_NONE`). **`Game` 구조체·장착 함수·스탯 계산은 바꾸지 않는다.**
- 그리기 쪽은 외형 ID만 알고 아이템은 모른다. 나중에 "외형 덮어쓰기(형상 변환)"를 넣어도 이 표만 바꾸면 된다(이번 범위 밖).

### 3.4 기준점(anchor)

셀마다 다음 값을 `art/hero/gear/anchors.json`에 기록한다. 좌표는 **그 셀이 속한 아틀라스의 셀 픽셀 공간**(0..192), 원본 방향(공격·기술은 왼쪽을 본 상태) 기준이다.

| 기준점 | 내용 | 쓰는 레이어 |
| --- | --- | --- |
| `foot` | 기존 발 기준점. 새로 정하지 않고 코드 값을 그대로 복사 | 전체 (흔들림 검사 기준) |
| `head` (x, y, 기울기, 보는 방향) | 정수리 아래 머리 중심 | 투구 |
| `neck`, `torso` (x, y, 기울기) | 목·가슴 중심 | 갑옷 덧장식(견갑 등) |
| `grip` (x, y), `blade` (각도, 길이), `weapon_depth` (앞/뒤) | 오른손 손잡이, 칼날 방향 | 무기 |
| `view` | 정지·걷기는 N..NW, 공격·기술은 "왼쪽 측면" 계열 | 투구·무기의 방향별 원화 선택 |

- 셀 크기가 모션마다 달라서 같은 투구를 놓을 때 배율이 다르다. 배율은 `192 / 그림 상자`(정지·걷기 56, 공격 64×프레임 배율, 기술 80)로 **자동 계산**하고 기준점 표에는 넣지 않는다.
- 자동 추정 후 사람이 검토 시트(셀 위에 점·선을 그린 PNG)로 확인한다. 위 시험처럼 손잡이 추정은 틀리기 쉽다.

### 3.5 레이어별 제작 방식

| 슬롯 | 방식 | 1차 예시 |
| --- | --- | --- |
| 무기 | **칼날 마스크 + 기준점 배치.** 베이스에서 지운 칼날 픽셀 = 기본 환도 레이어. 새 무기는 방향별 칼 원화를 `grip`·`blade`에 맞춰 놓고 손가락·몸 뒤 부분을 잘라 둔다 | 단련한 환도(`ITEM_SWORD`): 같은 환도 형태, 칼날 광택·놋쇠 코등이·손잡이 끈만 달리함. 길이·곡률은 기존과 거의 같게 |
| 갑옷 | **맞춤 덧칠.** 셀별 기본 갑옷 영역 마스크(붉은 허리띠·흰 깃·손·얼굴 제외)에 누비 질감·색을 입히고, 필요하면 `torso` 기준점에 작은 덧장식 | 누비 갑옷(`ITEM_ARMOR`): 남색/청록 계열 유지, 가로 누빔 줄과 솜 두께감. 붉은 허리띠 그대로 |
| 투구 | **기준점 배치.** 방향별 투구 원화(정지·걷기 8방향 + 공격·기술 측면 몇 장)를 `head`에 놓음. 상투는 전립 정수리 안에 가림 | 전립(戰笠): 검은 펠트 갓 모양 테, 붉은 상모(술), 작은 정자 장식. 깃털·뿔 같은 서양풍·화려한 장식 없음 |

세 레이어 모두 102셀 전체에 만든다. 장착했는데 공격 중에만 사라지는 일이 없게 하기 위해서다.

### 3.6 파일명·폴더

```
art/hero/gear/

  masks/<atlas>-blade.png           칼날 마스크 (베이스 아틀라스와 같은 크기)
  masks/<atlas>-armor.png           기본 갑옷 영역 마스크
  weapon/hwando-tempered/           방향별 원화, 프롬프트, preparation.json
  armor/nubi/                       질감 원화, 프롬프트, preparation.json
  helmet/jeonrip/                   방향별 원화, 프롬프트, preparation.json
assets/
  warrior-*-v1.png                  → 칼을 뺀 베이스로 교체 (파일명 유지 여부는 2단계에서 결정)
  gear/weapon-hwando-v1.png         기본 환도 레이어 (102셀 묶음)
  gear/weapon-hwando-tempered-v1.png
  gear/armor-nubi-v1.png
  gear/helmet-jeonrip-v1.png
scripts/prepare_gear_assets.py      마스크·기준점·원화 → 레이어 아틀라스 + src/hero_gear_data.h 생성
src/hero_gear_data.h                생성 파일: (외형, 아틀라스, 셀) → 묶음 안 사각형 + 셀 안 오프셋
```

- `<atlas>`는 기존 파일 이름에서 `warrior-`와 `-v1`을 뺀 것(`idle-8dir`, `walk-n` … `attack`, `cleave` …).
- 레이어는 102셀을 같은 격자로 두면 외형 하나당 텍스처가 약 15MB(RGBA)라 휴대폰에 부담이다. 그래서 **셀마다 내용이 있는 부분만 잘라 한 장에 묶고**, 원래 셀 안 위치는 생성 헤더에 둔다(`monster_atlas_data.h`와 같은 방식). 투구는 셀당 수십 px, 무기·갑옷도 셀의 일부라 묶음 한 장은 1~2MB 수준이 될 것으로 예상한다(2단계에서 실측).

### 3.7 렌더 시 합성

`gfx_hero`가 지금처럼 (아틀라스, 셀, 목적 사각형 `dest`, 반전 여부)를 한 번 계산한 뒤, 슬롯 순서대로 같은 변환으로 레이어를 그린다.

```
scale = dest.w / 192
x = 반전 ? dest.x + (192 - off.x - w) * scale : dest.x + off.x * scale
y = dest.y + off.y * scale
```

- 발 기준점 계산은 베이스 하나에서만 한다. 레이어는 같은 셀 공간에 있으므로 **발이 흔들릴 수 없다.**
- 반전은 베이스와 같은 플래그를 모든 레이어에 적용한다. 정지·걷기는 반전 없음 규칙이 그대로 유지된다.
- 무적 깜빡임 알파와 피격 번쩍임을 레이어마다 똑같이 적용한다(안 하면 장비만 번쩍이지 않는다).
- 추가 비용은 주인공 한 명당 그리기 호출 최대 3~4회. 렌더 타깃(오프스크린 합성)은 쓰지 않는다. WebGL·안드로이드 호환 위험을 피하기 위해서다.
- 레이어 텍스처는 시작할 때 불러온다(1차 외형 4개). 외형이 늘면 서장 그림처럼 장착할 때만 불러오기로 바꿀 수 있다.
- 게임 로직, 판정, 이동, 스탯은 바꾸지 않는다. 투구로 키가 몇 px 커지면 지붕 가림 상자 높이만 3단계에서 확인한다.

- **기본 외형 무변경:** 102셀 모두 "칼 뺀 베이스 + 기본 환도 레이어" 렌더가 지금 렌더와 픽셀 단위로 같은지 `test_hero_render`에서 검사.

## 6. 위험과 미해결

- 102셀 마스크·기준점 수작업이 2단계의 대부분이다. 품질이 낮으면 장비가 프레임 사이에서 떨린다.
- 공격 프레임의 베기 궤적은 베이스에 남긴다. 새 무기 색과 궤적 색이 어긋날 수 있다.
- 정지·걷기와 공격·기술의 복장 계열 차이는 그대로 남는다. 장비를 입혀도 공격 순간 옷 무늬가 바뀌어 보이는 현상은 기존 문제다.
- 가방 초상화(`warrior-v2.png`)는 1차에서 장비 외형을 반영하지 않는다.
- 웹 빌드는 `assets` 폴더 전체를 미리 내려받으므로 레이어만큼 첫 로딩이 늘어난다(2단계에서 실측).
